# 鸡尾酒推荐图片性能测试

## 已有机制与本次调整

- 推荐接口先拉取最多 100 条候选，随机展示 10 条；同一进程复用推荐结果。
- 图片使用独立磁盘缓存及 Flutter 解码缓存；缩略图按 142 × 173 逻辑像素乘 DPR 解码。
- 预取最多同时执行 3 个任务。注意：这是预取上限，不是整个页面的网络请求上限，Widget 展示也会发起请求。
- 先预取全部推荐缩略图，再预取前 2 项详情封面，而不是全部 10 项。其余详情封面仍在打开详情时正常加载。
- `preloadRecommendations(detailPreloadCount: 0)` 可用于对比“只加载缩略图”的实验；默认值为 2。
- 此调整减少非必要详情请求，不代表首张图片必然更快。实际效果取决于缓存命中、素材大小和其他页面请求。

## 1. 真机基线

使用 `flutter run --profile`，保留项目原有的设备、入口和环境参数。iOS profile 测试需要 macOS 和真机；不要用 debug 模式或模拟器帧率作为验收结果。

固定设备、网络、服务端素材和推荐 URL 集合。冷启动会重新随机推荐，因此比较两版时必须记录 URL，并尽量使用相同素材的数据夹具，否则样本大小不同会干扰结果。

记录以下时间点（可通过 DevTools Network、Performance 时间线及屏幕录制交叉核对）：

| 时间点 | 含义 |
| --- | --- |
| T0 | 首页推荐区域首次进入可视范围 |
| T1 | 推荐接口返回 |
| T2 | 第一张可见缩略图开始请求 |
| T3 | 该缩略图下载完成 |
| T4 | 对应真实图片首次显示，不是本地占位素材 |

接口可能在区域可见前开始，T1 也可能早于 T0，不要将差值强行归零。

- 接口等待：结合接口请求开始时间和 T1 判断，检查超时、候选池大小、后端查询。
- 调度等待：T2 - T1；缓存命中无网络请求时不适用。
- 网络耗时：T3 - T2；进一步拆为 DNS、连接、TLS、TTFB、下载。
- 解码/显示等待：T4 - T3；同时检查 UI/raster 帧时间及图片解码事件。
- 用户感知耗时：T4 - T0；还要记录首屏所有可见图片完成时间，避免只优化第一张。

DevTools Network 记录请求和体积；Performance 检查长帧；Memory 检查反复滚动和进出详情后的内存是否稳定。60 Hz 设备关注超过约 16.7 ms 的帧，120 Hz 设备关注约 8.3 ms。

## 2. 必测场景

| 场景 | 操作 | 关注点 |
| --- | --- | --- |
| 冷缓存 | 使用应用内推荐缓存清理功能，然后重新进入首页 | 首图时间、首屏完成时间、总下载字节 |
| 内存命中 | 同进程滚出推荐区再滚回 | 相同 URL/尺寸是否复用、是否闪烁 |
| 磁盘命中 | 保留磁盘缓存并重启 | 仅比较仍出现在新推荐中的相同 URL；过期文件可能后台重验证 |
| 弱网 | 真机限速，例如下行 1 Mbps、延迟 150 ms | 缩略图是否被无关图片抢占，滑动到后续卡片是否卡顿 |
| 详情 | 分别打开前两项及后续项 | 前两项封面预热、后续项按需加载、返回首页正常 |
| 错误/离线 | 断网或让测试素材返回 404 | 本地素材兜底、无崩溃、恢复后可正常加载 |
| 清理竞争 | 下载期间清理推荐缓存 | 无旧下载在清理后回写、不会影响其他业务缓存 |

每种场景至少采集 10 次，记录中位数和范围；需要看 P95 时建议至少 30～50 次。比较优化前后相同网络、素材下的首屏耗时、请求数、下载字节和长帧数量，而不是仅凭主观观感。

## 3. 单张图片网络测试

从 DevTools 取得实际请求 URL，在终端使用 curl 的 GET 请求（不要仅测 HEAD）：

```sh
curl.exe -L --max-time 30 -o NUL -sS -w "status=%{http_code} dns=%{time_namelookup}s connect=%{time_connect}s tls=%{time_appconnect}s ttfb=%{time_starttransfer}s total=%{time_total}s bytes=%{size_download} speed=%{speed_download}B/s\n" "实际图片URL"
```

上述为 Windows 命令；macOS/Linux 使用 `curl` 并将 `NUL` 换成 `/dev/null`。URL 需替换为实际地址。重复请求会温热服务端/CDN缓存，但 curl 默认不使用 Flutter 的磁盘缓存。测试会下载素材、产生网络流量；不要共享带签名或令牌的 URL。

使用 `-D` 将响应头保存到本地测试文件，检查 `Content-Type`、`Content-Length`（可能不存在）、`Cache-Control`、`ETag`、`Last-Modified`、`Age` 及 CDN 命中字段。下载内容应确实是图片，不能只看 HTTP 200；如跟随了重定向，需结合 Network 进一步分析各跳耗时。

以上时间是累计时间，`connect` 包含 DNS；不能直接将各字段相加。curl 的 TTFB 也包含连接和可能的重定向开销，不等于纯后端处理时间。

## 4. 根据数据决定下一步

1. **缩略图实际下载的是原图**：检查 API 的 `thumbnailUrl` 是否缺失。当前约定缺失时回退 `imageUrl`。优先让服务端稳定提供真实的 320px 缩略图，而不是在客户端猜测不存在的路径。
2. **图片字节太大**：服务端压缩并提供适合平台的 WebP/JPEG/PNG 变体，透明素材必须保留透明通道。可先以缩略图约 30～80 KB 作为试验目标，再通过真机清晰度确定；这不是现有素材的测量结果。客户端 ResizeImage 只控制解码，不减少原始网络字节。
3. **TTFB 高**：检查静态素材是否经过动态鉴权/实时变换，优先预生成缩略图、静态资源托管及 CDN。带版本 URL 可用长期缓存；同 URL 内容会变化时必须保留合适的过期和重验证策略。
4. **推荐接口慢**：优化候选查询、字段大小或设计专用推荐接口。缓存优先再刷新会改变“每次启动获取新候选”的语义，本次不擅自变更。
5. **下载快但显示慢**：确认解码缓存键和 DPR 一致，查看原图像素、解码事件和长帧，不要盲目提高预取并发或全局 ImageCache 容量。
6. **弱网仍有竞争**：进一步做可视区加相邻卡片的滚动窗口预取；需连同快速滑动、页面切换、清理竞争做回归，不建议直接一次性预热所有详情及配料。
